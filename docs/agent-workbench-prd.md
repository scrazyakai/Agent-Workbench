# Agent 通用工具台 PRD

- **版本：** V0.1
- **产品阶段：** MVP / 内部试用
- **技术方向：** Python + LangChain + LangGraph + React
- **首期范围：** Agent Builder、Tool Registry、Agent Runtime、Durable Execution、Workflow / Multi-Agent、Trace + Eval

> 本文按“面向企业内部研发团队、先支持单团队部署、后扩展多租户”的假设设计。技术栈中的 LangGrapg 按 LangGraph 理解。
>
> 首期优先打通“配置 → 调试 → 发布 → 执行 → 暂停与恢复 → 追踪与评测”的完整闭环，而不是一次做成完整低代码平台。

## 1. 产品定位

### 1.1 一句话定位

一个面向开发者的 Agent 开发与运行平台，让团队能够通过统一界面和 API，构建、发布、运行及评估可靠的 AI Agent 与多 Agent 工作流。

### 1.2 核心问题

| 当前问题 | 产品解决方式 |
| --- | --- |
| Agent 配置分散在代码中，难以协作和版本管理 | 统一 Builder 与发布版本 |
| 工具接口、凭证和权限不统一 | Tool Registry 集中注册和治理 |
| 运行接口不一致，缺少任务管理 | Agent Runtime 提供统一执行入口 |
| 长任务遇到进程重启、审批等待后难以继续 | Durable Execution 提供持久化状态与恢复 |
| 多 Agent 协作需要重复开发调度逻辑 | 基于 LangGraph 编排可控工作流 |
| 出错原因、调用成本和效果难以定位 | Trace + Eval 提供观测与回归评测 |

### 1.3 目标用户

| 角色 | 主要需求 |
| --- | --- |
| Agent 开发者 | 配置 Agent、接入工具、编排流程、调试发布 |
| 应用开发者 | 通过 API 调用 Agent、订阅事件、获取结果 |
| 业务专家 / 评测人员 | 维护样本、评估效果、审批敏感操作 |
| 平台管理员 | 管理模型、工具凭证、权限、运行资源 |

首期主用户为 Agent 开发者。业务用户直接使用 Agent 的门户、模板市场等不作为首期重点。

## 2. 产品目标与边界

### 2.1 首期目标

1. 用户能够创建一个带工具调用能力的 Agent，并发布为可调用版本。
2. 支持单 Agent 和受控的多 Agent 工作流。
3. 长任务支持持久化、审批暂停和故障恢复。
4. 每次运行能够追踪关键步骤、工具调用、Token 和成本。
5. 发布前能够通过固定数据集进行版本效果对比。

### 2.2 首期不做

- 任意复杂度的无代码工作流编辑器。
- 用户上传任意 Python 代码并直接在平台进程执行。
- 完全自主、无限循环的 Agent 群体协作。
- 完整知识库管理、文档解析和 RAG 数据治理。
- 模型训练、微调和模型托管。
- 商业计费系统、公共插件市场。
- 跨区域容灾与严格的全链路 exactly-once 执行。

范围约束：RAG、数据库查询等能力可以先作为注册工具接入，不单独建设子平台。

## 3. 核心业务闭环

```text
注册并测试工具
      ↓
创建 Agent / Workflow
      ↓
绑定模型、提示词、工具和运行策略
      ↓
Playground 调试与 Trace 查看
      ↓
执行离线评测
      ↓
发布不可变版本
      ↓
应用通过 API 发起 Run
      ↓
执行 / 审批 / 恢复 / 取消
      ↓
采集反馈，沉淀回归数据集
```

### 3.1 典型场景

#### 场景 A：工具型 Agent

开发者创建“运营数据助手”，绑定查询工具。用户提交问题后，Agent 查询数据并返回结构化分析结果。

#### 场景 B：长任务与人工审批

Agent 生成客户邮件，执行到发送步骤时暂停。审批人员查看收件人和正文，批准后继续执行；服务重启不应导致任务丢失。

#### 场景 C：多 Agent 分工

“研究 Agent”收集资料，“分析 Agent”形成结论，“审核 Agent”检查质量。审核不通过时按预设规则返回分析步骤，达到上限后停止。

#### 场景 D：版本回归

开发者修改提示词后，对同一数据集评估新旧版本，比较通过率、成本和延迟，再决定是否发布。

## 5. 模块需求

### 5.1 Agent Builder

#### 目标

将 Agent 的定义、调试和版本发布集中管理，减少重复编码。

#### 功能需求

| 功能 | 首期要求 |
| --- | --- |
| 基本信息 | 名称、描述、标签、负责人 |
| 模型配置 | 选择模型连接，配置温度、输出 Token 上限及超时 |
| 提示词 | 编辑系统提示词，支持显式声明的输入变量 |
| 输入输出 | JSON Schema 定义输入；支持文本或结构化输出 |
| 工具绑定 | 从 Registry 选择工具及工具版本 |
| 执行约束 | 最大步骤数、最大工具调用数、运行时限、Token 预算 |
| Playground | 输入测试数据，流式显示结果与执行步骤 |
| 版本管理 | 保存草稿、发布不可变版本、查看版本差异 |
| 发布与回滚 | 默认发布别名指向指定版本，支持回退 |

#### 核心规则

- 编辑只影响草稿，不影响已发布版本。
- Run 创建时固定 Agent、工具和模型配置引用，不随默认版本变更。
- 凭证只存引用，不写入提示词和版本快照。
- 发布前必须通过配置和依赖校验。
- 工具权限由服务端执行层校验，不能依赖提示词约束。

#### 验收标准

- 用户可从空白配置完成“创建 → 调试 → 发布 → API 调用”。
- 发布后继续修改草稿，线上版本行为配置不变。
- 缺失模型、无权限工具或无效 Schema 时阻止发布，并定位问题字段。

### 5.2 Tool Registry

#### 目标

建立统一、可测试、有版本和权限边界的工具目录。

#### 首期工具类型

1. HTTP 工具：调用预先配置的外部 API。
2. 受信任 Python 工具：由平台管理员通过代码部署注册。

后续扩展：MCP 工具、OpenAPI 批量导入。首期不开放任意代码上传执行。

#### 工具元信息

- 名称、说明、负责人、标签。
- 输入 / 输出 JSON Schema。
- 连接配置与凭证引用。
- 超时、并发限制、重试策略。
- 风险等级：只读、写入、高风险。
- 是否需要审批。
- 是否支持幂等，以及幂等键传递方式。
- 版本、启用状态、依赖引用关系。

#### 功能需求

| 功能 | 首期要求 |
| --- | --- |
| 注册和编辑 | 配置工具协议、参数和返回结构 |
| 测试 | 输入参数后试调用，展示脱敏结果与耗时 |
| 版本管理 | 发布版本不可变；Agent 绑定具体版本 |
| 凭证管理 | 加密保存、界面不可回显、日志脱敏 |
| 权限控制 | 控制哪些角色或 Agent 可以使用工具 |
| 风险控制 | 高风险调用在执行前触发审批 |
| 生命周期 | 支持停用；被引用版本不可直接删除 |

#### 安全规则

- HTTP 工具应配置目标地址允许列表，防止 SSRF。
- 普通用户不得通过参数替换任意请求目标或读取内部凭证。
- 工具结果作为不可信数据处理，不能自动提升调用权限。
- 紧急停用工具后，后续调用应明确失败，不绕过控制。

#### 验收标准

- Schema 不合法的调用在请求外部服务前被拒绝。
- 无权限调用返回明确错误码。
- 工具测试页与 Trace 中不出现原始密钥。
- 对具有副作用的工具，未配置安全策略时不得自动重试。

### 5.3 Agent Runtime

#### 目标

提供统一、可管理的 Agent 和 Workflow 执行服务。

#### 功能需求

| 功能 | 首期要求 |
| --- | --- |
| 创建运行 | 指定 Agent / Workflow 版本及输入 |
| 异步执行 | 返回 run_id，后台 Worker 执行 |
| 流式事件 | 通过 SSE 推送状态、输出片段和步骤事件 |
| 会话支持 | 使用 thread_id 关联多轮上下文 |
| 运行管理 | 查询、取消、查看失败原因 |
| 调度控制 | 排队、并发限制和基础配额 |
| 预算控制 | 限制步骤、时长、Token 和工具调用次数 |
| 结构化错误 | 区分模型、工具、权限、预算及系统错误 |

#### 运行状态

```text
queued → running → succeeded
                 → failed
                 → timed_out
                 → waiting_approval → queued
                 → waiting_input    → queued

非终态 → cancelling → cancelled
```

- Worker 中断不立即等于业务失败，应先判断是否可以恢复。
- 同一 thread_id 首期串行执行，避免会话状态并发覆盖。
- 取消是协作式取消，不承诺撤销已完成的外部操作。
- 预算采用执行前检查和执行后累计；在途请求可能产生有限超额。

#### 验收标准

- API 支持创建、查询、事件订阅和取消运行。
- 客户端断开 SSE 不影响后台执行。
- SSE 断线后可按事件游标继续读取，客户端可去重。
- 达到步骤上限时停止继续调度，并展示明确原因。

### 5.4 Durable Execution

#### 目标

使长时间任务在进程故障、审批等待和人工补充输入后能够可靠继续。

#### 功能需求

| 功能 | 首期要求 |
| --- | --- |
| Checkpoint | 持久化图状态、恢复位置与必要运行元数据 |
| 故障恢复 | Worker 重启后恢复具备恢复条件的运行 |
| 人工中断 | 支持执行前审批与人工补充输入 |
| 恢复操作 | 从持久化检查点继续执行 |
| 并发保护 | 防止多个 Worker 同时推进同一个 Run |
| 幂等控制 | 为外部副作用调用记录稳定的调用标识 |
| 恢复审计 | 记录触发原因、操作者、检查点和恢复次数 |

#### 关键语义

恢复不是重新运行：

- 恢复：继续原有 Run，保留原版本和检查点。
- 重新运行：创建新的 Run，记录其来源 Run。
- 首期不支持恢复时任意修改图结构、版本或内部状态。
- 审批绑定具体工具、规范化参数和调用标识；参数变化后必须重新审批。

可靠性边界：

- 图状态持久化不等于外部副作用只执行一次。
- 平台按可能重复投递设计，不承诺全链路 exactly-once。
- 写入类工具优先通过下游幂等键或结果查询避免重复。
- 无法判断外部操作是否成功时，进入人工处理状态，不能盲目重试。

#### 验收标准

- 在支持恢复的节点中断 Worker 后，可恢复到正确逻辑位置。
- 等待审批的任务在服务重启后仍可查询、审批和继续。
- 重复提交同一审批结果不会重复推进任务。
- 对具备幂等能力的工具，通过故障注入验证不会重复产生业务效果。
- 对结果不确定的非幂等操作，明确阻止自动重试。

### 5.5 Workflow / Multi-Agent

#### 目标

支持可预测、可调试的多步骤及多 Agent 协作，避免首期陷入无限制自主编排。

#### 首期节点类型

| 节点 | 用途 |
| --- | --- |
| Start / End | 定义流程输入输出 |
| Agent | 调用已发布 Agent 版本 |
| Tool | 执行注册工具 |
| Condition | 按结构化状态选择分支 |
| Human Approval | 暂停并等待审批 |

首期支持：

- 顺序执行。
- 条件分支。
- 多 Agent 分工链路。
- 带次数上限的审核循环。

后续支持：

- 并行与汇合。
- Supervisor 动态委派。
- 子工作流及更复杂的失败补偿。

#### 编排方式

首期采用“图结构预览 + 节点配置表单 + 简单连线编辑”。

不提供任意脚本节点。条件使用受限表达式或结构化规则。

#### 状态与版本规则

- Workflow 显式定义共享状态 Schema。
- 节点配置输入映射和输出写入字段。
- 默认只向 Agent 传递所需字段，不传递整个共享状态。
- 节点绑定具体 Agent / Tool 版本。
- 发布时检测无效边、孤立节点、缺失参数及无边界循环。

#### 验收标准

用户能够搭建并运行：

```text
资料收集 Agent
      ↓
分析 Agent
      ↓
审核 Agent
      ↓
通过？── 是 → 输出
  │
  否 → 返回分析，最多 2 次
```

Trace 能够定位每次循环、节点输入输出和失败位置。

### 5.6 Trace + Eval

#### 目标

回答两个问题：

1. 这次运行为什么成功或失败？
2. 这个版本是否比上一个版本更好？

#### A. Trace

采集范围：

- Run、节点及子 Agent 层级关系。
- 模型调用、工具调用、重试、审批、恢复事件。
- 输入输出摘要、耗时、错误信息。
- Token 用量和估算成本。
- Agent、Workflow、Tool 版本及配置标识。

展示能力：

- 时间线与节点树。
- 节点输入输出详情。
- 按状态、版本、时间、错误类型筛选。
- 从 Run 跳转到对应定义版本。
- 对敏感字段脱敏或禁止存储。

边界：展示可观测调用、公开输出和执行事件，不以获取模型隐藏思维链为目标。

#### B. Eval

| 功能 | 首期要求 |
| --- | --- |
| 数据集 | JSONL 导入、界面编辑、版本快照 |
| 样本字段 | 输入、参考答案 / 断言、标签 |
| 规则评测 | Schema 校验、精确匹配、字段断言 |
| 模型评测 | 可选 LLM Judge，记录评分依据和评测器版本 |
| 批量执行 | 对固定 Agent / Workflow 版本运行数据集 |
| 结果比较 | 新旧版本并列展示，通过率、延迟、成本 |
| 人工标注 | 对结果确认、纠错和补充备注 |

评测安全与可比性：

- 默认使用测试凭证或 Mock 工具，禁止评测触发生产高风险操作。
- 对比记录数据集快照、目标版本、模型配置及评测器版本。
- LLM Judge 评分不作为唯一发布依据。
- 对外部实时数据的变化明确标记，避免误判为版本退化。

#### 验收标准

- 可对同一数据集评测两个版本，并查看逐样本差异。
- 失败样本能够关联到对应 Trace。
- 评测配置和结果可复查；不承诺模型输出完全可重复。

## 6. 权限与平台基础能力

虽然不单独列为首期业务模块，以下能力属于必要基础设施。

| 角色 | 权限 |
| --- | --- |
| Admin | 模型连接、工具与凭证管理、成员权限、全局配置 |
| Developer | 编辑和发布 Agent / Workflow、调试、查看授权运行 |
| Operator | 运行、取消、按授权审批和恢复 |
| Viewer | 查看授权配置、运行与评测结果 |

补充要求：

- 凭证使用权与凭证明文读取权分离。
- 发布、权限变更、审批、恢复和凭证变更写入审计日志。
- 首期支持单 Workspace，数据模型保留 workspace_id。
- 未完成隔离验证前，不宣称支持安全的多租户托管。

## 7. 技术架构建议

```text
React Console
      │ REST / SSE
      ▼
FastAPI
├── 定义与版本管理
├── 工具注册与权限
├── Run / Approval API
└── Eval API
      │
      ▼
持久化任务调度 → Python Workers
                   ├── LangGraph 执行
                   ├── LangChain 模型与工具适配
                   └── 平台工具调用网关
      │
      ├── PostgreSQL：业务数据、检查点、执行记录
      ├── Redis：可选队列 / 缓存加速
      └── 对象存储：大体积输出、附件、评测产物
```

### 技术分工

| 技术 | 定位 |
| --- | --- |
| LangChain | 模型接口、工具适配、结构化输出 |
| LangGraph | 状态图、条件路由、中断和检查点执行 |
| 平台服务 | 身份权限、版本、调度、幂等、审计、产品 API |
| React | 配置、调试、运行观测和评测界面 |

关键约束：LangGraph 提供执行基础，但任务调度、外部副作用安全、权限和完整运营能力仍需平台实现并验证。

| Agent / AgentVersion | Agent 定义与发布快照 |

建议所有版本对象不可变；Run 固定引用版本，避免“同一个运行记录对应的配置后来变了”。

## 9. 对外 API 草案

```http
POST /v1/agents
POST /v1/agents/{id}/versions
```

## 10. 非功能要求

以下为建议初始验收目标，需根据部署规模通过压测确认。

| 维度 | 要求 |
| --- | --- |
| 接口性能 | 不含模型 / 工具耗时，创建 Run API P95 ≤ 500ms |
| 事件延迟 | 事件产生到前端展示 P95 ≤ 1s |
| 初始容量 | 在约定测试环境支持 20 个并发活跃 Run |
| 故障恢复 | 可恢复运行在故障检测后 60s 内重新进入调度 |
| 数据可靠性 | 已确认持久化的任务和审批不因单 Worker 重启丢失 |
| 安全 | 凭证加密、日志脱敏、服务端鉴权、出站网络控制 |
| 可观测性 | 所有 Run 有关联标识；遥测缺失需可检测 |
| 数据保留 | Trace 默认保留 30 天，支持配置与清理 |

## 11. 交付阶段

| 阶段 | 交付内容 | 完成标准 |
| --- | --- | --- |
| M1：单 Agent 闭环 | 基础权限、模型连接、Builder、HTTP / Python 工具、Runtime、基础 Trace | 一个工具型 Agent 可配置、发布并通过 API 调用 |
| M2：可靠执行 | Checkpoint、审批、恢复、幂等记录、取消与预算控制 | 长任务通过故障注入和重复提交测试 |
| M3：工作流闭环 | 顺序、分支、受限循环、多 Agent 节点、图级 Trace | 研究—分析—审核流程稳定运行 |
| M4：质量闭环 | 数据集、规则评测、版本对比、可选 LLM Judge | 新版本上线前可执行可复查的回归评测 |

不建议首期按六个独立子系统并行建设。应按上述纵向业务闭环交付，降低集成与返工风险。

## 12. 产品成功指标

### 核心指标

每周有效运行量：成功完成且通过用户确认或规则校验的非调试 Run 数。

### 辅助指标

- 首个 Agent 从创建到成功发布的耗时。
- 创建 Agent 后成功完成首次运行的用户比例。
- 平台故障导致的运行失败率。
- 可恢复故障的自动恢复成功率。
- 单次有效运行的成本和延迟。
- 发布版本的评测覆盖率。
- 重复副作用事件数及高风险越权调用数。

应分别统计“平台执行成功”和“业务答案正确”，不能用 HTTP 成功或 Run 完成替代效果指标。

## 13. 立项前需确认

1. **首个业务场景是什么？** 建议选择一个带真实工具调用、包含审批的场景验证全链路。
2. **部署模式是什么？** 内网私有化、企业云部署，还是面向外部用户的 SaaS？
3. **首批模型和工具有哪些？** 直接决定连接器和安全边界。
4. **是否涉及生产写操作？** 若涉及，审批与幂等必须随首个版本交付。
5. **预期并发及任务时长是多少？** 决定调度、存储和容量验收基线。

总体建议：将产品定位为“开发者优先的可靠 Agent 平台”，优先做好版本、运行状态、工具安全和可观测性，再逐步增强可视化编排。
